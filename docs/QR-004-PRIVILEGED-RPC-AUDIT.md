# QR-004 — Auditoría de RPC privilegiadas y autorización multiempresa

## Resumen ejecutivo

Auditoría del catálogo **efectivo** creado desde las 27 migraciones SQL versionadas de `main`, no de todas las declaraciones históricas. Se inspeccionaron 46 funciones `SECURITY DEFINER` de la aplicación y 4 funciones administradas por Supabase. En el catálogo de aplicación: todas las funciones son propiedad de `postgres`, fijan `search_path` vacío, ninguna tiene `EXECUTE` efectivo para `anon` y no hay concesiones `EXECUTE` a `PUBLIC`. Las 33 funciones en `public` son ejecutables por `authenticated`; 5 helpers/RPC en `private` también tienen permiso `authenticated`. La API PostgREST expone únicamente `public` y `graphql_public`, por lo que las funciones `private` no son rutas RPC de la Data API.

No se confirmó una vulnerabilidad en las pruebas ejecutadas. Esto no cierra QR-004: las pruebas dinámicas se limitaron a una RPC segura de cuota y a la suite de supervisores/dispositivos. Las funciones de asistencia y PIN se inspeccionaron estáticamente por la restricción P0 y no se invocaron.

## Alcance y evidencia

- Commit auditado: `f961f232f2261cb8fda1fbff63090389ae1ba8c5`.

`pgbouncer.get_auth(text)` (propietario `supabase_admin`, sin ejecución para roles cliente), `supabase_functions.http_request()` (propietario `supabase_functions_admin`, con grants de plataforma que incluyen anon/authenticated), y `vault.create_secret(...)` / `vault.update_secret(...)` (solo servicio/admin). No están en los esquemas expuestos por PostgREST de la aplicación. Revalidar si cambia `api.schemas` o el modelo de Supabase.

## Revisión de esquema, RLS, JWT y vistas

- `supabase/config.toml` limita los esquemas Data API a `public` y `graphql_public`; `private` no está expuesto. `authenticated` tiene `USAGE` sobre `private` para permitir sus helpers RLS dentro de PostgreSQL, mientras que `anon` no.
- Las 46 funciones de aplicación fijan `search_path` vacío; sus objetos se referencian con nombre de esquema.
- No se detectó uso de `user_metadata`/`raw_user_meta_data` en las definiciones efectivas de estas funciones. La aceptación por correo sí consulta el estado de Auth/identidad; la barrera de configuración de invitaciones está en `raw_app_meta_data` conforme a la migración vigente.
- Las dos vistas de aplicación, `public.attendance_session_totals` y `public.attendance_period_totals`, tienen `security_invoker=true`. Las vistas `extensions` y `vault` pertenecen a la plataforma y no se exponen por la Data API de la aplicación.
- Las migraciones activan RLS para las tablas públicas de negocio y aplican grants/policies; la suite reutilizada verifica aislamiento de empresas, sucursales, membresías y dispositivos. La prueba nueva comprueba que todas las tablas públicas efectivas tengan RLS.
- Las políticas permisivas de PostgreSQL se combinan por OR dentro de cada comando/rol; la revisión debe evaluar el conjunto de políticas, no cada política de forma aislada. No se observó una ruta que eluda las restricciones en los dominios cubiertos por QR-004 y QR-007.

## Riesgos y limitaciones

1. **No es un certificado exhaustivo de toda RPC y perfil.** La matriz dinámica nueva prueba el flujo seguro de cuota; los otros dominios se sustentan en suites locales previas y la suite específica reutilizada, cuya ejecución histórica no sustituye repetirlas en este commit.
2. `authenticated` posee EXECUTE SQL directo sobre cinco funciones `private`; la API no expone ese esquema. Cambiar la lista de esquemas de PostgREST requiere revisar estos grants antes de exponerlo.
3. Las RPC de asistencia tienen grants a `authenticated` y contienen efectos de negocio; su autorización se inspeccionó estáticamente, pero la comprobación dinámica se bloqueó intencionalmente por QR-003 P0.
4. `private.review_attendance_adjustment` tiene EXECUTE para authenticated vía SQL. La definición valida `auth.uid()` y `attendance.review_adjustments`; su comportamiento no se invocó por la prohibición de operaciones de asistencia. Evidencia anterior documenta revisión a nivel de empresa, no sucursal; pendiente de revalidación dinámica cuando se autorice el dominio.
5. No se consultó Testing ni Producción. La reconstrucción local demuestra comportamiento del código canónico, no estado remoto ni ausencia de cambios manuales remotos.
6. No se modificó lógica funcional ni migraciones; el alcance publicado contiene solo runner, suite SQL y documentación.
