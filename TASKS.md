## QR-001 — Enlaces de acceso

- **Objetivo:** mostrar en administración enlaces permanentes para supervisores (`/scanner`) y empleados (`/mi-qr`), con opciones para copiar y compartir.
- **Criterios de aceptación:** el administrador ve las URLs del origen actual sin datos de empresa/usuario; los destinos exigen sesión autenticada y membresía/permisos activos; copiar y compartir tienen alternativa funcional si Web Share no está disponible; otras empresas no pueden alterar el acceso.
- **Evidencia requerida:** rutas y controles revisados; pruebas de permisos, copiar/compartir y acceso denegado documentadas.
- **Referencias iniciales:** `src/app/(supervisor)/scanner/page.tsx`, `src/app/(employee)/mi-qr/page.tsx`, `src/app/(admin)/admin/configuracion/page.tsx`.
- **Resultado:** configuración muestra enlaces absolutos construidos desde el `APP_BASE_URL` validado: `/scanner` y `/mi-qr`. Copiar admite Clipboard API y fallback DOM; compartir usa `https://wa.me/?text=...` codificado y sin número. El texto compartido no incluye datos de empresa o persona.
- **Retorno de autenticación:** las rutas protegidas conservan un destino cerrado (`/scanner` o `/mi-qr`) en el login. Solo se usa si coincide con el rol activo; múltiples membresías siguen requiriendo selección explícita. Las invitaciones pendientes conservan prioridad. El retorno no acepta URLs externas ni parámetros arbitrarios.
- **Seguridad revisada:** las páginas siguen comprobando sesión y membresía activa por rol. El API del portal valida empleado activo y expediente vinculado; el contexto del escáner mantiene autorización de dispositivo y sucursal.
- **Pruebas:** `node --experimental-strip-types --test tests/access-links.test.mjs` pasó (6/6); `npm run test:user-access` pasó (6/6); `npm run lint`, `npm run typecheck`, `npm test` y `npm run build` terminaron con código 0. Node mostró avisos existentes de módulos TypeScript sin `type: module` durante las pruebas; no hubo fallos.

## QR-002 — Invitaciones manuales

- **Objetivo:** permitir invitaciones individuales compartibles por WhatsApp, conservando el flujo actual por correo y usando Supabase Auth de forma segura.
- **Criterios de aceptación:** token individual de un solo uso, expiración y revocación comprobadas en servidor; destinatario verificado y vinculado al flujo Auth; el token no otorga permisos sin autenticación/membresía activa; rate limiting/auditoría y protección ante enumeración evaluadas; correo actual sigue funcionando.
- **Evidencia requerida:** modelo de amenazas breve, pruebas para expiración/revocación/destinatario/reutilización y regresión del correo.
- **Referencias iniciales:** `src/lib/access/`, `src/app/(auth)/invitacion/`, `src/app/api/admin/access/`, `INVITATION-FLOW-TESTING.md`, `supabase/migrations/20261012143000_company_user_access_management.sql`.
- **Diseño implementado para revisión:** las invitaciones manuales reutilizan la invitación individual por correo existente. El enlace es adicional, de un solo uso, expira junto con la invitación y exige sesión Supabase Auth con correo confirmado idéntico al destinatario. Las cuentas nuevas completan primero el alta/verificación por el correo Auth existente; el registro público permanece deshabilitado.
- **Resultado local:** la corrección en PR #7 permite aceptar por correo incluso cuando existe enlace WhatsApp; ambos caminos verifican Auth, correo confirmado, destinatario, expiración, autorización y membresía. La aceptación bloquea la fila, marca una sola vez y borra el hash para invalidar el canal alterno. Se conserva el flujo de reenvío de correo.
- **Pruebas:** `npm run test:security:matrix:local` pasó con las 156 aserciones pgTAP originales, más regresiones HTTP/Auth de aceptación por correo con enlace, invalidación mutua, repetición, regeneración, concurrencia entre canales y owner-only para enlaces de invitación admin. Mailpit confirmó el correo HTTP 201 y el reenvío HTTP 200; runner verificó limpieza. Pasaron lint, typecheck, `npm test` (70) y build aislado sin `.env*`. Solo avisos conocidos de Node `MODULE_TYPELESS_PACKAGE_JSON` y trazado standalone por `node_modules` enlazado. No se accedió a Testing ni Producción.
- **Estado:** la implementación y las regresiones de convivencia por correo/WhatsApp están en el PR #7 fusionado en `main`; QR-002 permanece **En curso** por su dependencia de cierre de QR-004. Riesgo residual operativo: una persona sin cuenta depende del correo de verificación inicial. Evidencia del diseño y pruebas: [INVITATION-FLOW-TESTING.md](INVITATION-FLOW-TESTING.md).

## QR-003 — Verificar persistencia de fallos de PIN

- **Objetivo:** reproducir y verificar la persistencia de intentos fallidos; reutilizar la corrección versionada existente si resuelve la causa.
- **Criterios de aceptación:** reproducir el flujo legacy y el corregido en una base local desechable; comprobar contador, bloqueo, expiración y ausencia de evento cuando el PIN no es válido; documentar causa raíz y pruebas.
- **Restricción de tarea:** las migraciones se aplican solo en bases locales desechables para esta verificación. No ejecutar cambios, RPC de prueba ni migraciones en Testing o Producción; coordinar cualquier despliegue remoto en una tarea autorizada separada.
- **Diagnóstico:** las versiones anteriores de `scan_employee_attendance` y `confirm_employee_attendance` lanzaban una excepción después de que `private.verify_employee_pin` incrementaba el contador. La excepción abortaba la transacción y revertía el incremento.
- **Corrección en el repositorio:** ya existe `supabase/migrations/20261018120000_persist_employee_pin_failures.sql`. Ambas RPC devuelven un rechazo estructurado `pinError` sin lanzar una excepción después de verificar el PIN. No se creó ni duplicó una migración.
- **Reproducción local:** en un stack Supabase desechable con migraciones hasta `20261012143000`, preview y confirm devolvieron SQLSTATE `22023` y el contador quedó en 0. Tras aplicar la migración existente solo en esa base local, preview y confirm devolvieron `pin_invalid`, el contador persistió en 1 y 2, y no se creó ningún evento de asistencia.
- **Pruebas:** `npm run test:pin-lockout` pasó (3/3); `npm run test:pin-lockout:db` pasó (pgTAP 35/35 e integración PostgreSQL); la integración verificó intentos concurrentes, bloqueo de cinco intentos por 15 minutos, expiración, reset, dispositivo no autorizado/revocado y aislamiento entre empresas. `npm test`, lint, typecheck y build también pasaron; detalles en [docs/PIN-LOCKOUT-FIX.md](docs/PIN-LOCKOUT-FIX.md).
- **Auditoría remota de solo lectura:** al 2026-10-28 Testing registra 24 migraciones; QR-003 y QR-002 no constan aplicadas. Las RPC de escaneo aún lanzan excepción por PIN inválido. Se compararon los 23 SQL con nombres comunes, ACL y estructura de dependencias relevante. Informe y manifiesto con hashes: [docs/QR-003-MIGRATION-RECONCILIATION.md](docs/QR-003-MIGRATION-RECONCILIATION.md) y [docs/QR-003-TESTING-MIGRATION-MANIFEST.csv](docs/QR-003-TESTING-MIGRATION-MANIFEST.csv).
- **Resultado de preparación:** el push desde los timestamps canónicos de `main` falla en dry-run con `DbPushMissingLocalError`. Un manifiesto temporal reconstruido con los 24 SQL archivados de Testing más QR-003 mostró solo QR-003 pendiente; la simulación local y pgTAP 35/35 pasaron. No se ejecutó repair ni escritura remota.
- **Respaldo/recuperación:** la POC local de pg_dump cifrado GnuPG, SHA-256 y restore limpio pasó 56/56; confirmó Auth local, RLS, RPC y grants sintéticos. No consultó ni exportó datos alojados. La última consulta de Testing mostró `backups: []` y PITR apagado; no hay restore remoto probado. Detalle: [docs/QR-003-BACKUP-RECOVERY-PLAN.md](docs/QR-003-BACKUP-RECOVERY-PLAN.md).
- **Riesgo/pendiente:** NO-GO para escritura hasta confirmar un respaldo recuperable, aprobar costos/custodia y probar restauración aislada alojada o aprobar alternativa de recuperación. Cualquier cambio manual ajeno a funciones/tablas inspeccionadas sigue sin descartarse. Aplicación y validación sintética con escritura en Testing requieren autorización separada. No volver a las definiciones de `20261012030630`, que reintroducirían la excepción.

## QR-004 — Seguridad multiempresa

- **Objetivo:** auditar RLS, sesiones, permisos, `SECURITY DEFINER`, sucursales, credenciales QR y dispositivos autorizados.
- **Criterios de aceptación:** matriz rol × operación × empresa/sucursal; inventario de funciones privilegiadas y grants; pruebas negativas entre empresas y membresías inactivas; hallazgos con evidencia, severidad, mitigación y pruebas de regresión.

- **Resultado fase 2:** `tests/qr004-auth-matrix.local.integration.mjs` y `supabase/tests/qr004_scanner_authorization_test.sql` ejecutaron 142 aserciones pgTAP en un stack local desechable: tenant/RLS y roles, sucursales, membresías y revocaciones, RPC de acceso, ACL de credenciales, escáner directo, cruce de empresa/sucursal, dispositivo desconocido, QR revocado y ausencia de eventos/sesiones ante denegaciones. Sin intentos de PIN incorrectos.
- **Resultado fase 3:** se extendió el mismo runner y el job CI existente para usar Auth local, sesiones SSR reales sintéticas y un servidor Next.js temporal. Pasaron las rutas `GET/POST/PATCH /api/admin/access`, reenvío de invitaciones, `GET /api/me`, `GET /api/employee/portal`, `/admin`, `/mi-qr`, auditoría y catálogo de permisos; también las RPC de invitación válida, vencida, revocada, destinatario no coincidente, consumo y repetición. Se comprobaron `company.manage`, selección multiempresa, revocación de membresía y snapshots sin cambios ante rechazos. Las Server Actions conservan cobertura unitaria; no se enviaron peticiones HTTP inventadas. El catálogo `/api/admin/permissions` requiere solo membresía activa owner/admin válida y permite consultar metadatos aunque `company.manage` tenga override denegado; auditoría y accesos requieren `company.manage`.
- **Ampliación de cobertura local (29-oct-2026):** el runner ahora prueba también `GET/POST /api/employees`, `GET/PATCH /api/employees/[id]`, `GET/POST/PATCH /api/branches`, `GET/PATCH /api/supervisors` y `GET /api/supervisor-devices`. - **Asistencia y horarios (29-oct-2026):** el runner cubre `GET /api/attendance`, detalle de jornada, guardia de dispositivo en `/api/attendance/scan`, `GET/POST /api/schedules`, modificación de estado, asignaciones y calendario. GitHub Actions CI pasó (job `verify`, run 40998745615) para el commit de código `e59bd02c7975c7c244398e873b2fd7b6c86566c9`. No se accedió a Testing/Producción ni se ejecutó QR-003.
- **Diagnóstico:** no se confirmó una vulnerabilidad nueva en los casos cubiertos. La invitación local válida devolvió HTTP 201 y el reenvío HTTP 200, ambos mediante Auth SMTP/Mailpit del stack desechable. El reenvío no modificó datos.
