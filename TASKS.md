## QR-001 — Enlaces de acceso

- **Objetivo:** mostrar en administración enlaces permanentes para supervisores (`/scanner`) y empleados (`/mi-qr`), con opciones para copiar y compartir.
- **Criterios de aceptación:** el administrador ve las URLs del origen actual sin datos de empresa/usuario; los destinos exigen sesión autenticada y membresía/permisos activos; copiar y compartir tienen alternativa funcional si Web Share no está disponible; otras empresas no pueden alterar el acceso.
- **Evidencia requerida:** rutas y controles revisados; pruebas de permisos, copiar/compartir y acceso denegado documentadas.
- **Referencias iniciales:** `src/app/(supervisor)/scanner/page.tsx`, `src/app/(employee)/mi-qr/page.tsx`, `src/app/(admin)/admin/configuracion/page.tsx`.
- **Resultado:** configuración muestra enlaces absolutos construidos desde el `APP_BASE_URL` validado: `/scanner` y `/mi-qr`. Copiar admite Clipboard API y fallback DOM; compartir usa `https://wa.me/?text=...` codificado y sin número. El texto compartido no incluye datos de empresa o persona.
- **Retorno de autenticación:** las rutas protegidas conservan un destino cerrado (`/scanner` o `/mi-qr`) en el login. Solo se usa si coincide con el rol activo; múltiples membresías siguen requiriendo selección explícita. Las invitaciones pendientes conservan prioridad. El retorno no acepta URLs externas ni parámetros arbitrarios.
- **Seguridad revisada:** las páginas siguen comprobando sesión y membresía activa por rol. El API del portal valida empleado activo y expediente vinculado; el contexto del escáner mantiene autorización de dispositivo y sucursal.
- **Pruebas:** `node --experimental-strip-types --test tests/access-links.test.mjs` pasó (6/6); `npm run test:user-access` pasó (6/6); `npm run lint`, `npm run typecheck`, `npm test` y `npm run build` terminaron con código 0. Node mostró avisos existentes de módulos TypeScript sin `type: module` durante las pruebas; no hubo fallos.

## QR-002 — Invitaciones manuales

- **Objetivo:** permitir invitaciones individuales compartibles por WhatsApp, conservando el flujo actual por correo y usando Supabase Auth de forma segura.
- **Criterios de aceptación:** token individual de un solo uso, expiración y revocación comprobadas en servidor; destinatario verificado y vinculado al flujo Auth; el token no otorga permisos sin autenticación/membresía activa; rate limiting/auditoría y protección ante enumeración evaluadas; correo actual sigue funcionando.
- **Evidencia requerida:** modelo de amenazas breve, pruebas para expiración/revocación/destinatario/reutilización y regresión del correo.
- **Referencias iniciales:** `src/lib/access/`, `src/app/(auth)/invitacion/`, `src/app/api/admin/access/`, `INVITATION-FLOW-TESTING.md`, `supabase/migrations/20261012143000_company_user_access_management.sql`.
- **Diseño implementado para revisión:** las invitaciones manuales reutilizan la invitación individual por correo existente. El enlace es adicional, de un solo uso, expira junto con la invitación y exige sesión Supabase Auth con correo confirmado idéntico al destinatario. Las cuentas nuevas completan primero el alta/verificación por el correo Auth existente; el registro público permanece deshabilitado.
- **Resultado local:** la corrección en PR #7 permite aceptar por correo incluso cuando existe enlace WhatsApp; ambos caminos verifican Auth, correo confirmado, destinatario, expiración, autorización y membresía. La aceptación bloquea la fila, marca una sola vez y borra el hash para invalidar el canal alterno. Se conserva el flujo de reenvío de correo.
- **Pruebas:** `npm run test:security:matrix:local` pasó con las 156 aserciones pgTAP originales, más regresiones HTTP/Auth de aceptación por correo con enlace, invalidación mutua, repetición, regeneración, concurrencia entre canales y owner-only para enlaces de invitación admin. Mailpit confirmó el correo HTTP 201 y el reenvío HTTP 200; runner verificó limpieza. Pasaron lint, typecheck, `npm test` (70) y build aislado sin `.env*`. Solo avisos conocidos de Node `MODULE_TYPELESS_PACKAGE_JSON` y trazado standalone por `node_modules` enlazado. No se accedió a Testing ni Producción.
- **Estado:** **Hecha** para el alcance funcional implementado y validado; PR #7 está fusionado en `main`. El canal compartible no reemplaza la autenticación ni la verificación del destinatario. Una persona sin cuenta depende del correo de verificación inicial. Requisitos de liberación y aceptación integral se controlan en QR-011; este cierre no autoriza despliegue. Evidencia: [INVITATION-FLOW-TESTING.md](INVITATION-FLOW-TESTING.md).

## QR-006 — Estabilidad del escáner

- **Objetivo:** investigar cámara, conexión, concurrencia, mensajes de error y reintentos.
- **Criterios de aceptación:** escenarios reproducibles en viewports móviles emulados, permisos de cámara, pérdida de conexión, solicitudes paralelas y respuestas obsoletas; estados visibles sin filtrar detalles; reintentos controlados para consultas idempotentes. Escaneos repetidos, PIN y asistencia permanecen bloqueados por QR-003.
- **Evidencia inicial:** `src/components/scanner/mobile-scanner.tsx`, rutas `src/app/api/attendance/scan/route.ts` y `src/app/api/supervisor/scanner/context/route.ts`, pruebas `tests/scanner-context.test.mjs`.
- **Hallazgo reproducido:** con `getUserMedia` demorado, dos activaciones rápidas iniciaban dos adquisiciones (la prueba esperaba una y observó dos). El componente no tenía una guarda síncrona ni estado de arranque; si ambas adquisiciones terminaban, solo el último control quedaba referenciado para detenerse.
- **Corrección y fail-closed:** una referencia síncrona y un identificador de generación evitan arranques paralelos y descartan inicializaciones que terminan después de desmontar, cambiar empresa o perder autorización. El cierre para cámara, el desmontaje y el fin de autorización detienen las pistas explícitamente. Si el contexto devuelve error o se pierde la red, el escáner limpia la autorización y la lectura en memoria; al recuperar red o foco, consulta de nuevo el contexto real.
- **Experiencia de cámara y conexión:** errores distintos para dispositivo inexistente, permiso denegado, cámara ocupada y configuración incompatible; el botón indica el estado mientras se inicializa y bloquea otra activación. La sesión expirada, autorización revocada, selección requerida, límite temporal y falla 5xx muestran mensajes seguros. Los errores terminales 401/403/409 pausan el sondeo hasta foco o reconexión; fallas 429/5xx mantienen solo el sondeo fijo de 12 s.
- **Pruebas locales:** la ampliación cubre 22 casos E2E en Chromium con Supabase desechable: cámara, red, estados de dispositivo pendiente/rechazado/aprobado/revocado, códigos HTTP, respuestas de contexto fuera de orden, petición pendiente durante cambio de empresa/desmontaje, y ausencia de overflow horizontal a 320/390/430/768 px. El backend de autorización usa Route Handlers y PostgreSQL locales; cámara y respuestas puntuales de error se simulan.
- **Resultados adicionales:** la matriz QR-004 local pasó con 201 aserciones pgTAP y pruebas HTTP/Auth; `npm test` pasó con una prueba GnuPG omitida porque el sandbox bloqueó el socket del agente; lint, typecheck y build pasaron. El build usó directorio temporal sin `.env.local` y valores locales ficticios; Next informó 27 archivos omitidos del standalone por `node_modules` enlazado fuera del temporal.
- **Estado:** **Hecha** para las correcciones y pruebas automatizadas documentadas; PR #21 fue fusionado. **Limitaciones transferidas a QR-011:** hardware Android/iPhone y permisos reales no se certifican con Chromium emulado. No se certifica con este E2E la asistencia integral, el PIN ni el registro de eventos; QR-003 ya corrigió y validó sintéticamente el lockout. No se hicieron pruebas físicas en esta fase.
